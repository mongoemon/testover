Why Characterization Testing
Who does it, when, and what to pair it with

Written up from a discussion about managing legacy systems, which ran from “is E2E regression enough?” to “is this a QA or a Dev job?”. Each point is checked against testover to show how we use the idea and where we differ from the textbook.

01Why do characterization testing

A characterization test records what the system actually does today, not what it should do, and locks it so any change in behaviour shows up immediately.

The principle

  • No trustworthy spec. Long-lived systems have stale documentation, and you cannot wait for a complete spec before touching the code. The running system acts as the test oracle.
  • Restructuring without knowing what broke. E2E checks only what its author thought of. Small side effects, such as one field with a drifted value, slip through.
  • Some bugs already have dependants. Customers or other systems may rely on the behaviour. Fixing it must be a decision, not a side effect of a refactor.
  • Low cost. Treat the system as a black box: feed inputs, record outputs, compare. No need to decode the business logic line by line first.

Why E2E regression alone is not enough

  • Coarse. It tells you a screen broke, not which field drifted.
  • Slow. Minutes to hours, so it cannot serve as the feedback loop while refactoring.
  • Flaky. Network blips and selector changes get mixed up with real logic failures, so causes are hard to separate.
  • Combinations do not scale through a UI. Deeply nested conditions are impractical to drive from the screen, while a function-level test can run hundreds of inputs in seconds.

In short: E2E is the coarse outer net that checks the main user flows still work. Characterization is the fine inner net fitted tightly around the code you are about to restructure. They complement each other; neither replaces the other.

What it does in testover

testover has no written spec; the real behaviour lives in the code and localStorage. So tests/characterization/ holds 42 tests in 3 files: validation.spec.ts and resilience.spec.ts lock input boundaries and how the app boots from damaged storage, and golden-master.spec.ts compares the whole localStorage with a committed snapshot. 3 of them are named QUIRK:, odd behaviours recorded as they are: a new password is stored in plain text, a tb.users value stored as an array locks everyone out, and the first change after loading invalid tasks permanently drops them.

02Versus other kinds of test

They differ in who the oracle is and how finely they check.

KindOracleChecksLevel / speedIf red, it means
E2E / Full regressionHuman-defined requirementsOnly the values you chose to assertWhole system · minutes to hoursThe system differs from what it should be
CharacterizationThe system’s behaviour todayWhole output or state, or observable boundariesFunction to API · seconds (in testover, driven through a browser)Behaviour changed; decide whether on purpose
ContractAn agreed interfaceStructure and types at the boundarySystem edge · secondsOne side broke the agreement
Visual snapshotAn approved baseline imageScreen pixelsScreen · seconds to minutesThe look changed; review the diff

Two points that are easy to mix up:

  • Characterization is dynamic testing. The code must run to produce the output, even though the result is stored as a static file. It is not static testing.
  • E2E can act as characterization if it asserts on a whole page (visual) or a whole payload. In practice the two overlap rather than one being a subset of the other.

03Who does it, and when

In the textbook, characterization is mainly a developer task because it touches code and needs seams. QA contributes inputs and judges results. In testover the tests drive the UI and need no code surgery, so QA can write them directly.

04Workflow when you must refactor

  1. Lay the outer net with E2ECover the critical flows before touching code (in testover: the 5 @smoke tests plus journey, login, tasks and profile).
  2. Lay the inner net with characterizationLock the module you will restructure using varied inputs. Record outputs as they are, odd parts included.
  3. Judge the odd partsDev decides intended or bug. Name them QUIRK: so they are easy to find.
  4. Refactor, running characterization oftenIt must stay 100% green. Red means behaviour changed, so decide before moving on.
  5. Finish with full E2E and visualConfirm the restructured piece still fits with the rest before release.

05Tools to pair

Each layer covers the gaps of the others. Shown with generic tools and what testover actually uses.

Outer · E2E regression checks main user flows still work → generic: Playwright, Cypress, WebdriverIO · testover: Playwright with a Page Object (tests/support/pages.ts)
Inner · Characterization locks behaviour of the code you will restructure → generic: ApprovalTests, Verify, Jest/Vitest snapshots, Syrupy · testover: plain assertions in validation/resilience plus a Golden Master using toMatchSnapshot() in golden-master.spec.ts (masking helper in tests/support/golden.ts)
At the edge · Contract locks the minimum agreement consumers need → generic: Pact, schema validation · testover: zod in contracts/schemas.mjs
Appearance · Visual snapshot catches UI drift while other tests stay green → Playwright toHaveScreenshot() in Docker (Linux) · testover: tests/visual.spec.ts, 5 screens
Fast · Unit logic that needs no browser, and where characterization tests are later converted to → node:test · testover: unit/*.test.mjs
Orchestration · CI ordered fast to slow to save resources → GitHub Actions / GitLab CI · testover: smoke.yml (unit + smoke on every PR), weekend-e2e.yml (full suite)

Practices that make it workable

Mask unstable valuesReplace timestamps, UUIDs and tokens with constants before comparing, or the test is red on every run. For visual tests, mask regions and disable animation.
Seams and mocksCut out real DBs, external APIs and the clock with DI or fakes so runs are repeatable (testover starts from seedable storage).
Tags and per-layer commandsnpm run test:characterization, test:contract, test:smoke, test:visual
Fail-fast CI orderStage 1: lint, unit, characterization (fast) → Stage 2: E2E smoke → Stage 3: full suite and visual on a schedule

Characterization and contract together when splitting a system

When carving a new service out of an old one (Strangler Fig), send identical input to both and require identical output (characterization), while the new API must not break the agreement with frontend or mobile clients (contract).

06Cautions

  • Green does not mean correct. A passing characterization test means “unchanged”, not “right”. Bugs need an owner’s decision, not a permanent QUIRK label.
  • Locking too much is brittle. Whole-output comparison goes red when a new field appears, unlike a consumer-driven contract where an extra field usually does not break anyone. (In testover the schemas are deliberately .strict(), so a new field is a conscious contract change.)
  • A red image is not always a bug. Decide the same way: intended means update the baseline, unintended means fix the UI.
  • Updating the master is a decision. Do not run --update-snapshots just to get green.
  • It is scaffolding. Once the module is clean, replace it with unit tests that state intent.

testover uses both styles: explicit per-behaviour assertions (validation, resilience), which state intent clearly, and a Golden Master (golden-master.spec.ts) that compares the whole localStorage with a snapshot to catch fields nobody thought of. It uses Playwright’s toMatchSnapshot() with masked timestamps/UUIDs and sorted keys. Snapshots are plain text, so they can be generated on any OS (unlike visual baselines, which need Docker on Linux). Update with npm run test:characterization -- --update-snapshots and always read the diff before committing. Caveat: the snapshots record the plain-text password because that is the real behaviour today; fixing that QUIRK means updating the snapshots in the same change.
