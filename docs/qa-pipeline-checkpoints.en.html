                  05Rules QA uses to review the whole pipeline

                  Use these as questions when you review a workflow file or when the team wants to add or drop a job.

                  Sources: [5][7][9][13][14][15]

                  Build once, promote the same artifact

                  What passed in test and staging must be the same artifact that goes to production, identified by commit SHA or version.

                  Avoid: rebuilding when you deploy to prod

                  Gates must actually block

                  Important checks must be required checks in branch protection, not a red mark that still lets you merge.

                  Avoid: continue-on-error on core tests

                  Every flaky test has an owner

                  Quarantine a test that passes only sometimes, with a ticket and a fix date. Do not re-run until it goes green.

                  Avoid: a silent 3× retry on every test

                  Results readable without opening logs

                  Keep a combined report such as Allure, with screenshots, traces and video on failure, and keep enough history to see trends.

                  Avoid: digging through 3,000 log lines to find what broke

                  Controlled test data and environments

                  Seed fresh data on every run instead of relying on leftovers, and make each environment's config traceable.

                  Avoid: a test that passes because someone created data yesterday

                  Never go green by deleting tests

                  A PR that deletes or skips a test must say why and get a QA review. A missing test is missing coverage.

                  Avoid: test.skip without a ticket

                  In short: QA checks three things in a pipeline: order (cheap before expensive), gates (red really stops), and evidence (the report says what was tested, on which version, with what result).
