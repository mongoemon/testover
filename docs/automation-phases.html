02รายละเอียดแต่ละ Phase

ทุกข้อใน “ใน testover” ตรวจกับไฟล์จริงในรีโปแล้ว

0เลือกสิ่งที่จะ automate (Discover & Risk)

ตัดสินใจว่า test อะไรคุ้มที่จะเขียนเป็นโค้ด และอะไรไม่ควร

QA

  • ไล่ user journey สำคัญ (สมัคร → login → จัดการ task → แก้โปรไฟล์)
  • จัดลำดับตามความเสี่ยงและความถี่ที่ต้อง regression
  • แยกสิ่งที่ควร test มือ เช่น look-and-feel ออก

Dev

  • บอกจุดที่เปราะหรือเพิ่งแก้บ่อย
  • บอกขอบเขตข้อมูลที่ app เก็บ (localStorage, API) และใครเป็นเจ้าของ
  • ยืนยันว่า env ที่ใช้ test รันซ้ำได้ (npm start)

ใน testover: journey หลักกลายเป็น tests/journey.spec.ts, login, tasks, profile

เงื่อนไขทางออก: มีรายการ journey เรียงตามความเสี่ยง และตกลงกันแล้วว่า “ไม่ automate” อะไร

1วางฐานเครื่องมือ (Foundation)

ทำให้การเขียน test ครั้งต่อไปเร็ว และไม่พังเมื่อ UI เปลี่ยน

QA

  • ตั้ง Playwright, config, Page Object (tests/support/pages.ts)
  • ทำ helper อ่าน/เขียน storage (tests/support/storage.ts)
  • กำหนด tag: @smoke @contract @characterization @security @destructive

Dev

  • ให้ selector ที่เสถียร (role, label, test id) ไม่ผูกกับ CSS
  • ทำให้ app เริ่มจากสถานะที่รู้ได้ (seed data / บัญชี demo)
  • แจ้งเมื่อเปลี่ยนโครง DOM ก่อน merge

ใน testover: playwright.config.ts, tests/support/, docs/tags.md

เงื่อนไขทางออก: เขียน test ใหม่ด้วย Page Object ได้โดยไม่ต้อง copy selector

2ตกลง Contract ที่ขอบระบบ (Contract)

เขียน “ข้อตกลง” ระหว่างส่วนต่าง ๆ ให้เป็นโค้ดที่รันได้ ก่อนที่ test จำนวนมากจะพึ่งมัน

QA

  • แปลงข้อตกลงเป็น zod schema ใน contracts/schemas.mjs
  • เขียน test ที่ตรวจว่า app และสคริปต์ “เคารพ” schema จริง
  • ทำ fixture ตัวอย่างทั้งกรณี pass / fail / ว่าง

Dev

  • เป็นคนบอกว่าข้อมูลที่ถูกต้องหน้าตาเป็นอย่างไร (ความยาว ชนิด field บังคับ)
  • review schema ว่าตรงเจตนา ไม่ใช่แค่ตรงโค้ดปัจจุบัน
  • ถ้าจะเพิ่ม field ใหม่ ต้องแก้ schema ใน PR เดียวกัน

ใน testover: C1 localStorage → tests/contracts/storage.spec.ts · C2 รายงาน Playwright และ C3 body ของ webhook → unit/contracts.test.mjs Schema เป็น .strict() โดยตั้งใจ field ใหม่จึงเป็นการเปลี่ยน contract อย่างรู้ตัว

เงื่อนไขทางออก: ทุกขอบเขตที่ข้ามระบบมี schema เดียว ที่ทั้ง unit และ Playwright import ใช้ร่วมกัน

3บันทึกพฤติกรรมปัจจุบัน (Characterization)

ล็อก “สิ่งที่ app ทำจริงตอนนี้” ก่อนแก้หรือ refactor เพื่อให้เห็นทันทีว่าอะไรเปลี่ยน

QA

  • ไล่ boundary: username 2/3/20/21 ตัวอักษร, อักขระต้องห้าม, trim/lowercase
  • ไล่สถานะผิดปกติ: ข้อมูลใน storage เสียหรือผิดชนิด
  • ตั้งชื่อ test ที่เป็นพฤติกรรมแปลก ๆ ว่า QUIRK: เพื่อค้นง่าย

Dev

  • ตัดสินใจเป็นรายข้อว่าพฤติกรรมนี้ “ตั้งใจ” หรือ “บั๊ก”
  • บั๊ก → เปิด ticket แล้วแก้ test พร้อมโค้ด
  • ตั้งใจ → ปล่อยไว้ และเขียนเหตุผลเป็นคอมเมนต์

ใน testover: tests/characterization/validation.spec.ts และ resilience.spec.ts และ golden-master.spec.ts (snapshot ของ localStorage ทั้งก้อน 5 ชุดใน tests/__screenshots__/characterization/) รวม 42 test มี 3 ตัวชื่อ QUIRK เช่น รหัสผ่านใหม่ถูกเก็บเป็น plain text, หรือ array ใน tb.users ทำให้ทุกคนล็อกอินไม่ได้ (ฝั่ง unit ก็มี characterization ของข้อความ notify ด้วย)

เงื่อนไขทางออก: ทุก boundary ที่จะแตะมี test ที่ผ่านด้วยพฤติกรรมปัจจุบัน และ QUIRK ทุกข้อมีเจ้าของตัดสินใจ

4test ระดับ feature (Unit · E2E · A11y)

ครอบคลุมพฤติกรรมที่ตั้งใจให้มี ตามปิรามิด: unit เร็ว, E2E ครอบ journey

QA

  • เขียน E2E ตาม journey ที่จัดลำดับไว้ใน phase 0
  • เพิ่ม a11y ด้วย axe และ test ด้านความปลอดภัย (@security)
  • ดู flaky และ assertion ที่อ่อนเกินไป

Dev

  • เขียน unit test ของ logic ที่ไม่ต้องใช้ browser (unit/*.test.mjs)
  • review test ของ QA ว่าตรง requirement
  • เพิ่ม test ใน PR เดียวกับ feature ใหม่

ใน testover: E2E ใน tests/*.spec.ts, a11y ใน tests/a11y.spec.ts รวม 137 Playwright test ใน 10 ไฟล์ (5 smoke, 12 security, 5 visual)

เงื่อนไขทางออก: feature ใหม่ทุกตัวมี test อย่างน้อยหนึ่งชั้นก่อน merge

5ต่อเข้า CI (Gate & Report)

ให้ test รันเอง และบอกผลถึงคนที่ต้องรู้

QA

  • เลือกชุดที่ gate PR (@smoke) กับชุดเต็มที่รันตามเวลา
  • ตั้ง report (Allure) และการแจ้งเตือน (scripts/notify.mjs)

Dev

  • ดูแล workflow / secret / environment
  • รับผิดชอบ build ที่แดงบน PR ของตัวเอง

ใน testover: smoke.yml รัน unit + smoke ทุก push/PR · weekend-e2e.yml รันชุดเต็มทุกเสาร์-อาทิตย์ 09:00 เวลาไทย พร้อม unit, Allure และแจ้งเตือน · cloudflare-pages.yml publish docs และ report

เงื่อนไขทางออก: PR ที่ทำให้ smoke/unit/contract แดง merge ไม่ได้ และผลชุดเต็มถึงทีมโดยไม่ต้องมีคนไปกด

6ดูแลต่อเนื่อง (Maintain)

กัน test เน่า และเปลี่ยนสิ่งที่ test เปิดเผยให้เป็นการตัดสินใจ

QA

  • triage ผลรายสัปดาห์: บั๊กจริง / flaky / test ล้าสมัย
  • แยก test ที่ไม่เสถียรออกมา quarantine แล้วตามแก้
  • อัปเดตเอกสาร tag และตัวเลข

Dev

  • เมื่อ characterization/contract แดง ตัดสินว่า “แก้ app” หรือ “แก้ expectation”
  • แก้ QUIRK ที่เป็นบั๊ก แล้วเปลี่ยนชื่อ test ให้อธิบายพฤติกรรมที่ถูก

ใน testover: หัวไฟล์ characterization เขียนไว้ตรง ๆ: ถ้าแดง ให้ตัดสินใจอย่างรู้ตัวก่อน แล้วจึงอัปเดต expectation

เงื่อนไขทางออก: ไม่มี test แดงค้างโดยไม่มีเจ้าของ

03Contract vs Characterization

สองอย่างนี้มักถูกสับสน ต่างกันที่ “ยึดอะไรเป็นความจริง”

Contract testing

  • ยึด ข้อตกลงที่ควรเป็น เป็นความจริง
  • เขียนก่อนหรือพร้อมการออกแบบ ผ่านการตกลงของ Dev และ QA
  • ถ้าแดง = ฝ่ายใดฝ่ายหนึ่งผิดข้อตกลง ต้องแก้ฝั่งนั้น
  • ตรวจที่ขอบ: ข้อมูลใน storage, รายงาน, webhook
  • สัญลักษณ์: @contract, contracts/schemas.mjs

Characterization testing

  • ยึด สิ่งที่ app ทำจริงวันนี้ เป็นความจริง
  • เขียนทีหลังจากสังเกต โดยไม่ตัดสินว่าถูกผิด
  • ถ้าแดง = พฤติกรรมเปลี่ยน ต้องตัดสินว่าตั้งใจหรือไม่
  • ตรวจที่ input และขอบเขต: ความยาว อักขระ ข้อมูลเสีย
  • สัญลักษณ์: @characterization, ชื่อ QUIRK:

เมื่อ test เหล่านี้แดง ใครทำอะไร

Test แดง
↓
เป็น Contract หรือ Characterization?
↓
Contract → หาว่าใครผิดข้อตกลงแล้วแก้ฝั่งนั้น หรือเปิด PR แก้ schema พร้อมเหตุผล (Dev + QA เซ็นร่วมกัน)
↓
Characterization → Dev ตัดสิน: ตั้งใจเปลี่ยน? แก้ expectation / เป็นบั๊ก? แก้ app
↓
อัปเดตเอกสารและชื่อ test (ถ้าเคยเป็น QUIRK ให้เปลี่ยนชื่อ)

ลำดับ: กับโค้ดที่มีอยู่แล้ว (legacy) มักทำ Characterization ก่อน Contract เพราะต้องเห็นของจริงก่อนจึงตกลงได้ว่าควรเป็นอะไร ใน testover จัด Contract เป็น phase 2 เพราะ test ชั้นถัดไป import schema ร่วมกัน สลับลำดับสองขั้นนี้ได้โดยไม่กระทบขั้นอื่น

05จุดส่งต่องานที่ต้องตกลงให้ชัด

จุดเหล่านี้คือที่ที่ automation มักพัง เมื่อสองฝ่ายเข้าใจไม่ตรงกัน

SelectorDev แจ้งก่อนเปลี่ยน DOM; QA ใช้ role/label ก่อน และใช้ test id เมื่อจำเป็น
Seed dataDev รับประกันบัญชี demo และสถานะเริ่มต้น; QA ไม่พึ่งข้อมูลที่ test อื่นสร้าง
การเปลี่ยน Contractแก้ contracts/schemas.mjs ใน PR เดียวกับโค้ด และให้ QA รีวิว
QUIRKQA พบ → Dev ตัดสิน “ตั้งใจ/บั๊ก” → บันทึก ticket หรือเหตุผลไว้
Definition of Donefeature ต้องมี test อย่างน้อยหนึ่งชั้นก่อน merge และ smoke ต้องเขียว
ผลชุดเต็มQA triage ผลรายสัปดาห์ Dev รับ ticket ที่เป็นบั๊กจริง

06Visual snapshot testing

เทียบภาพหน้าจอจริงกับภาพอ้างอิง (baseline) เพื่อจับ UI ที่เพี้ยนทั้งที่ test อื่นยังผ่าน อยู่ในชั้น phase 4 ต่อจาก E2E

คืออะไรtest เปิดหน้า เตรียมสถานะ แล้วเรียก toHaveScreenshot() เทียบ pixel กับภาพที่ commit ไว้ ต่างเกินเกณฑ์ (1%) จึงแดง ต่างจาก screenshot: only-on-failure ที่แค่เก็บภาพไว้ดูตอนพัง
ใน testovertests/visual.spec.ts 5 หน้าจอ ติด @visual: login, register ตอน error, task board, task board แบบ dark, profile · baseline อยู่ที่ tests/__screenshots__/
สร้าง baseline ที่ไหนใน Docker image ของ Playwright (Linux) ผ่าน npm run test:visual:update ไม่ใช่บน Windows หรือ Mac เพราะ font และ anti-aliasing ต่างกันและจะทำให้ CI แดง
QA ทำเลือกหน้าจอที่คุ้มทำ, เตรียมสถานะให้นิ่ง (ข้อมูลตายตัว ปิด animation), เปิดดูภาพทุกครั้งก่อน commit baseline
Dev ทำบอกเมื่อตั้งใจเปลี่ยนหน้าตา, อนุมัติ baseline ใหม่ใน PR เดียวกับการเปลี่ยน UI, แจ้งค่าที่เปลี่ยนเองทุกครั้ง เช่น เลขเวอร์ชัน วันที่ เพื่อ mask
ข้อควรระวังภาพแดง ≠ บั๊กเสมอไป ต้องดู diff แล้วตัดสินแบบเดียวกับ characterization: ตั้งใจ → update baseline, ไม่ตั้งใจ → แก้ UI · ป้ายเวอร์ชันมุมขวาล่างอาจเปลี่ยนทุก release
