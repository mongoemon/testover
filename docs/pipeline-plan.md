# แผน pipeline ตามช่วงเวลา

[English](pipeline-plan.en.md) · คู่มือ tag: [tags.md](tags.md) (หัวข้อ 8: Priority)

เอกสารนี้ตอบว่า "ช่วงไหนควรรันชุดเทสอะไร" โดยใช้ tag `@p0` `@p1` `@p2` เป็นตัวเลือกชุด
ตัวเลขทุกตัววัดจริง ไม่ได้ประมาณ ยกเว้นที่ระบุว่า "ประมาณ"

## 1. ข้อมูลที่วัดมา

| อะไร | ผล | วัดจาก |
|---|---|---|
| `@p0` | 17 เคส, 6.1 วินาที | เครื่อง local, 2 workers, retries 0 |
| `@p0` + `@p1` | 120 เคส, 22.6 วินาที | เหมือนข้างบน |
| ทุกเคสยกเว้น `@visual` | 151 เคส, 32.5 วินาที | เหมือนข้างบน |
| unit | 122 เคส, ~6 วินาที | `node --test` |
| PR ล่าสุดที่ผ่าน (Smoke) | ทั้ง run 2 นาที 8 วินาที, check `smoke` เสร็จที่ 1 นาที 45 วินาที | GitHub Actions run 39194593232 (2026-10-19) |

เวลาของ job ใน run นั้น:

| Job | Setup (npm ci + เบราว์เซอร์) | เทสจริง |
|---|---:|---:|
| unit | 8 วินาที | 3 วินาที |
| contract | 24 วินาที | 6 วินาที |
| smoke-e2e | 24 วินาที | 6 วินาที |
| characterization | 36 วินาที | 15 วินาที |
| report (Allure) | 10 วินาที + Java | 6 วินาที |

**ข้อสรุปที่สำคัญ:** เทสทั้งหมดใช้เวลาไม่ถึง 40 วินาที แต่ PR รอ 1 นาที 45 วินาที เพราะ
(1) แต่ละ job ติดตั้งเองซ้ำ 24–36 วินาที และ (2) job ต่อกันเป็นลำดับ (unit/contract → smoke-e2e/characterization)
คอขวดตอนนี้คือโครงของ pipeline ไม่ใช่จำนวนเทส การแบ่ง priority จึงเป็นการเตรียมรับตอนชุดเทสโตขึ้น
ส่วนการลดเวลาตอนนี้ได้จากการรวม job (ข้อ 3)

## 2. แผนตามช่วงเวลา

| ช่วง | ทริกเกอร์ | รันอะไร | เป้าเวลา | ถ้าพัง |
|---|---|---|---|---|
| ก่อน push | เครื่อง dev | `npm run test:p0` | < 20 วินาที | แก้ก่อน push |
| Pull request | `pull_request` | unit + `check:tags` + `@p0\|@p1` ใน **job เดียว** | ~1 นาที (ประมาณ) | บล็อก merge (required check `smoke`) |
| หลัง merge | push เข้า `main` | ทุกเคสรวม `@p2` และ `@visual` | ~2 นาที | แจ้ง webhook, แก้ทันที |
| สุดสัปดาห์ | cron เสาร์-อาทิตย์ 09:00 ไทย (มีอยู่แล้ว) | ทุกเคส + รายงาน Allure + publish Pages + แจ้งผล | ~3 นาที | แจ้ง webhook |
| ก่อน release | `workflow_dispatch` | ทุกเคส (เลือก tag ได้: `@p0`, `@p0\|@p1`) | ~3 นาที | ห้าม release |
| ตรวจ flaky (ตัวเลือก) | cron รายวัน | `@p0` ซ้ำ `--repeat-each=5` `--retries=0` | ~1 นาที | แยกเคสเป็น `@flaky` |

ทำไม PR รัน `@p0|@p1` ทั้งที่ชื่อชั้นเร็วคือ `@p0`: ที่ขนาดนี้ `@p0|@p1` ใช้ 22.6 วินาทีเทียบกับ `@p0` 6.1 วินาที
ต่างกัน 16 วินาที แต่ครอบคลุมเกือบทุกฟีเจอร์ จึงคุ้มกว่า ให้ลดเหลือ `@p0` เมื่อถึงเกณฑ์ในข้อ 4

## 3. ทำให้ลื่นไหน ไม่ติดขัด

1. **รวมเป็น job เดียวใน PR:** ติดตั้งครั้งเดียว (~30 วินาที) แล้วรัน unit ตามด้วย Playwright
   ประมาณการ: 30 + 3 + 23 + upload ~2 = ~1 นาที จากเดิม 1 นาที 45 วินาที (ยังไม่ได้ทดลองบน Actions)
2. **เอา Allure report ออกจากเส้นทางวิกฤต:** ตอนนี้ job `report` ไม่ได้บล็อก check `smoke` อยู่แล้ว แต่ทำให้ run ยาวขึ้น 25 วินาที
   ให้สร้างเฉพาะหลัง merge หรือตอนเทสพัง
3. **fail fast:** รัน unit ก่อนใน job เดียวกัน ถ้าพังไม่ต้องเปิดเบราว์เซอร์ และใส่ `--max-failures=5` ใน PR เพื่อไม่เสียเวลารอเมื่อพังหนัก
4. **`concurrency` + `cancel-in-progress`:** มีอยู่แล้ว คงไว้
5. **tag ครบเสมอ:** step `npm run check:tags` ใน job `unit` ทำให้เคสใหม่ที่ไม่มี priority หรือมีสองตัว ทำให้ PR ไม่ผ่าน
6. **flaky:** CI ตั้ง `retries: 2` ซึ่งซ่อนเคสไม่เสถียร รายงาน `summary.mjs` แสดงรายการ "Flaky" อยู่แล้ว
   ถ้าเคสไหนปรากฏซ้ำ ให้ย้ายออกจากชุด gate ด้วย tag `@flaky` และตามแก้ อย่าเพิ่ม retries

## 4. เกณฑ์ปรับแผนเมื่อชุดเทสโต

| อาการ | ทำอะไร |
|---|---|
| job เทสของ PR เกิน 5 นาที | PR รันแค่ `@p0`, ย้าย `@p1` ไปรันหลัง merge |
| เกิน 10 นาที | แบ่ง shard `--shard=1/N` ในหลาย job (matrix) พร้อมรวมรายงานด้วย `merge-reports` |
| `@p0` เกิน 20% ของทั้งหมด | ทบทวน: ทุกเคสกำลังกลายเป็น p0 ให้ลดระดับเคสที่ไม่เคยจับบั๊ก |
| เคส fail แบบสุ่มซ้ำภายในเดือนเดียว | ติด `@flaky` แล้วแก้สาเหตุ |
| เทสมาก แต่ส่วนที่แก้น้อย | พิจารณา path filter หรือ test impact analysis (ระวัง: required check ต้องยังรายงานผล) |

## 5. สิ่งที่ยังไม่ได้ทำ

- ยังไม่ได้แก้โครง job ใน `smoke.yml` (รวม job) เพราะเป็น required check ของ branch protection ควรตัดสินใจร่วมกันก่อน
- ยังไม่ได้ตั้ง cron รายวันและ tag `@flaky`
- ตอนนี้ push เข้า `main` ยังรันชุดเดียวกับ PR (Smoke) ส่วนทุกเคสรวม `@p2`/`@visual` รันเฉพาะสุดสัปดาห์หรือสั่งเอง แถว "หลัง merge" ในตารางจึงเป็นเป้าหมาย ยังไม่ใช่ของที่ตั้งไว้แล้ว
- ตัวเลขเวลาของ "job เดียว" เป็นประมาณการ ต้องลองรันบน Actions เพื่อยืนยัน
