testover · Characterization Testing

ทำไมต้องทำ Characterization
ใครทำ ทำตอนไหน ใช้อะไรคู่กัน

เรียบเรียงจากบทสนทนาเรื่องจัดการระบบเก่า (legacy) ที่ไล่ตั้งแต่ “E2E regression พอไหม” ไปจนถึง “QA หรือ Dev เป็นคนทำ” แล้วตรวจกับ testover จริงว่าเรานำแนวคิดนี้มาใช้อย่างไร และส่วนไหนต่างจากตำรา

ทำไมต้องทำเทียบกับ test อื่นใครทำช่วงไหนลำดับการทำงานเครื่องมือที่ใช้คู่กันข้อควรระวังอ้างอิง

01ทำไมต้องทำ Characterization

Characterization test บันทึกว่า “ตอนนี้ระบบทำอะไรจริง” ไม่ใช่ “ควรทำอะไร” แล้วล็อกไว้เพื่อให้เห็นทันทีเมื่อพฤติกรรมเปลี่ยน

เหตุผลเชิงหลักการ

  • ไม่มีสเปกที่เชื่อถือได้ ระบบที่ใช้มานานมักเอกสารล้าสมัย จะรอให้สเปกครบก่อนแตะโค้ดไม่ได้ ระบบปัจจุบันจึงทำหน้าที่เป็นตัวเฉลย (test oracle)
  • รื้อโดยไม่รู้ว่าพังอะไร E2E ตรวจเฉพาะสิ่งที่คนเขียนนึกถึง ผลข้างเคียงเล็ก ๆ เช่น ฟิลด์ที่ค่าเพี้ยนไปหลุดได้ง่าย
  • บั๊กบางตัวมีคนพึ่งอยู่แล้ว ลูกค้าหรือระบบอื่นอาจชินกับพฤติกรรมนั้น การแก้ต้องเป็นการตัดสินใจ ไม่ใช่ผลพลอยได้ของ refactor
  • ต้นทุนต่ำ มองระบบเป็นกล่องดำ โยน input บันทึก output แล้วเทียบ ไม่ต้องแกะ business logic ทีละบรรทัดก่อน

ทำไม E2E regression อย่างเดียวไม่พอ

  • หยาบ รู้แค่ว่าหน้าจอพัง ไม่รู้ว่าฟิลด์ไหนเพี้ยน
  • ช้า รันเป็นนาทีหรือชั่วโมง ใช้เป็น feedback loop ตอน refactor ไม่ได้
  • Flaky พังเพราะเครือข่าย หรือ selector เปลี่ยน ปนกับพังเพราะ logic จริง แยกสาเหตุยาก
  • ยิงทุก combination ผ่านหน้าจอไม่ไหว เช่น เงื่อนไขซ้อนหลายชั้น ขณะที่ test ระดับ function ยิง input หลายร้อยแบบได้ในวินาที

สรุปสั้น ๆ: E2E คือตาข่ายหยาบชั้นนอก ตรวจว่า user flow หลักไม่ตาย Characterization คือตาข่ายละเอียดชั้นใน ประกบก้อนโค้ดที่กำลังจะรื้อ สองอย่างเสริมกัน ไม่ได้แทนกัน

ใน testover ทำเพื่ออะไร

testover เป็นแอปที่ไม่มีสเปกเขียนไว้ พฤติกรรมจริงอยู่ในโค้ด (ทั้งหน้าเว็บและ API) เราจึงมี tests/characterization/ จำนวน 46 test ใน 4 ไฟล์ (validation.spec.ts, resilience.spec.ts ที่ล็อก boundary ของ input, การ boot จาก storage ที่เสีย และตอน server ติดต่อไม่ได้, golden-master.spec.ts ที่เทียบ state ทั้งก้อนกับ snapshot และ network-golden.spec.ts ที่เทียบ response ของ server กับ request ของเบราว์เซอร์) ตัวที่ชื่อ GUARD: คือพฤติกรรมที่เคยเป็น QUIRK: (รหัสผ่านเป็น plain text, id ของงานถูกใช้ซ้ำ) แล้วถูกแก้ตอนย้ายไป backend การบันทึกตามจริงก่อนจึงช่วยให้เห็นว่าการย้ายครั้งนั้นเปลี่ยนอะไรบ้าง

02เทียบกับ test ชนิดอื่น

ต่างกันที่ “ใครเป็นตัวเฉลย” และ “ตรวจละเอียดแค่ไหน”

ชนิดตัวเฉลย (oracle)ตรวจอะไรระดับ / ความเร็วถ้าแดงแปลว่า
E2E / Full regressionRequirement ที่มนุษย์กำหนดเฉพาะค่าที่ตั้งใจตรวจทั้งระบบ · นาที–ชั่วโมงระบบผิดจากที่ควรเป็น
Characterizationพฤติกรรมของระบบวันนี้ผลลัพธ์/สถานะทั้งก้อน หรือ boundary ที่สังเกตได้function–API · วินาที (ใน testover รันผ่าน browser)พฤติกรรมเปลี่ยน ต้องตัดสินว่าตั้งใจหรือไม่
Contractข้อตกลงที่ตกลงกันไว้โครงสร้างและชนิดข้อมูลที่ขอบระบบขอบระบบ · วินาทีฝ่ายใดฝ่ายหนึ่งผิดข้อตกลง
Visual snapshotภาพ baseline ที่อนุมัติแล้วpixel ของหน้าจอหน้าจอ · วินาที–นาทีหน้าตาเปลี่ยน ต้องดู diff

สองจุดที่ต้องไม่สับสน

  • Characterization เป็น dynamic testing เพราะต้องรันโค้ดจริงเพื่อได้ output แม้ผลลัพธ์จะถูกเก็บเป็นไฟล์นิ่ง ไม่ใช่ static testing
  • E2E เป็น characterization ได้ ถ้าเปลี่ยนวิธี assert เป็นเทียบทั้งหน้า (visual) หรือทั้ง payload แต่ในทางปฏิบัติทั้งสองทับซ้อนกัน ไม่ใช่ subset กันทั้งหมด

03ใครทำช่วงไหน

ในตำรา characterization เป็นงานของ Dev เป็นหลักเพราะต้องแตะโค้ดและเจาะ seam ส่วน QA ช่วยออกแบบ input และตัดสินผล ใน testover ซึ่งทดสอบผ่าน UI ไม่ต้องเจาะโค้ด QA จึงลงมือเขียนได้เอง

ช่วงกิจกรรมDevQA
ก่อนแตะโค้ดตั้ง E2E smoke คลุม flow หลักเป็นตาข่ายนอกให้ selector เสถียร + seed dataเขียน/รันชุด E2E
ก่อนแตะโค้ดออกแบบ input และ edge case (boundary, ข้อมูลเสีย, เคสธุรกิจแปลก ๆ)บอกจุดเปราะที่รู้ออกแบบด้วย equivalence partitioning / boundary value
ก่อนแตะโค้ดเขียน characterization และบันทึก outputระดับ function/class (เจาะ seam ด้วย DI/mock) ส่วนใหญ่เป็นงาน Devระดับ API / UI / visual (ใน testover QA เขียนเอง)
ก่อนแตะโค้ดตัดสินผลที่แปลก: ตั้งใจหรือบั๊กตัดสินทีละข้อ ตั้งใจ = เขียนเหตุผล บั๊ก = เปิด ticketรีวิวว่าเป็น feature จริงที่ผู้ใช้พึ่งอยู่หรือไม่ ตั้งชื่อ QUIRK
ระหว่าง refactorรันซ้ำทุกครั้งที่แก้ (feedback loop วินาที)รันเองในเครื่อง—
หลัง refactorรัน E2E ชุดเต็มใน CI ปิดท้ายดูแล workflowเลือกชุด + triage ผล
เมื่อแดงตัดสินว่าแก้ app หรือแก้ expectationแก้ app ถ้าไม่ตั้งใจอัปเดต master/expectation ถ้าตั้งใจ แล้วแจ้งเอกสาร
หลังเสร็จเปลี่ยน characterization ที่เป็นนั่งร้านให้เป็น unit test ที่อ่านรู้เรื่องทำรีวิว

อ่านคู่กับ: Phase 3 ในหน้า Automation ทีละ Phase ที่ระบุตำแหน่งของ characterization ในแผน 7 phase

04ลำดับการทำงานเมื่อต้อง refactor

  1. วางตาข่ายนอกด้วย E2Eคลุม critical flow ก่อนแตะโค้ด (ใน testover คือ @smoke 5 ตัว และ journey/login/tasks/profile)
  2. วางตาข่ายในด้วย characterizationล็อกโมดูลที่จะรื้อ ด้วย input หลากหลาย บันทึก output ตามจริง รวมส่วนที่แปลก
  3. ตัดสินส่วนที่แปลกDev ตัดสินว่าตั้งใจหรือบั๊ก ตั้งชื่อ QUIRK: ให้ค้นง่าย
  4. Refactor โดยรัน characterization ถี่ ๆต้องผ่าน 100% ถ้าแดงคือพฤติกรรมเปลี่ยน ต้องตัดสินก่อนไปต่อ
  5. ปิดท้ายด้วย E2E เต็มชุด และ visualยืนยันว่าชิ้นที่รื้อยังต่อกับส่วนอื่นได้ ก่อนปล่อย

05เครื่องมือที่ต้องใช้คู่กัน

แต่ละชั้นปิดช่องโหว่ของอีกชั้น แสดงทั้งเครื่องมือทั่วไปและที่ testover ใช้อยู่จริง

ชั้นนอก · E2E regression ตรวจว่า user flow หลักยังไม่ตาย → ทั่วไป: Playwright, Cypress, WebdriverIO · testover: Playwright + Page Object (tests/support/pages.ts)
ชั้นใน · Characterization ล็อกพฤติกรรมของก้อนที่จะรื้อ → ทั่วไป: ApprovalTests, Verify, Jest/Vitest snapshot, Syrupy · testover: assertion ตรง ๆ ใน validation/resilience + Golden Master ด้วย toMatchSnapshot() ใน golden-master.spec.ts (ตัวช่วย mask ที่ tests/support/golden.ts)
ที่ขอบระบบ · Contract ล็อกข้อตกลงขั้นต่ำที่ผู้ใช้ข้อมูลต้องการ → ทั่วไป: Pact, schema validation · testover: zod ใน contracts/schemas.mjs
หน้าตา · Visual snapshot จับ UI ที่เพี้ยนทั้งที่ test อื่นผ่าน → Playwright toHaveScreenshot() + Docker (Linux) · testover: tests/visual.spec.ts 5 หน้าจอ
เร็ว · Unit logic ที่ไม่ต้องใช้ browser และเป็นที่ที่ characterization มักถูกแปลงไปอยู่ในภายหลัง → node:test · testover: unit/*.test.mjs
ควบคุม · CI เรียงเร็วไปช้า ประหยัด resource → GitHub Actions / GitLab CI · testover: smoke.yml (unit + smoke + characterization ทุก PR), weekend-e2e.yml (ชุดเต็ม)

Tag และคำสั่งรันเฉพาะชั้นnpm run test:characterization, test:contract, test:smoke, test:visual

Prism และ Mockoon: เครื่องมือฝั่ง API ทำอะไรได้

ทั้งสองตัวทำงานจากไฟล์ spec แบบ OpenAPI (ใน testover คือ contracts/openapi.yaml) ซึ่งเป็น contract ฉบับที่คนอ่านได้ ต่างจาก zod ที่เป็นโค้ด ไฟล์เดียวกันจึงใช้ได้ทั้งเป็นเอกสาร ใช้ตรวจ และใช้สร้าง mock

เครื่องมือทำอะไรเป็นชั้นไหนใน testoverข้อจำกัด
Prism (proxy mode)ตั้งหน้า API จริง ตรวจทุก request และ response กับ spec แล้วรายงานจุดที่ไม่ตรงContract: ตรวจว่า API จริงยังทำตามข้อตกลงnpm run contract:prism รัน api.spec.ts ผ่าน Prism ผ่านทั้ง 9 เคส และเมื่อลบฟิลด์ done ออกจาก spec Prism ฟ้องทันทีเห็นเฉพาะสิ่งที่เทสเรียก และเคสที่ส่ง request ผิดโดยตั้งใจจะมี request violation เป็นปกติ จึงดูเฉพาะ response
Mockoonสร้าง mock server จาก spec ให้ front end คุยด้วยได้ตอนยังไม่มี back endSeam / mock: ตัดของจริงออกเพื่อให้รันซ้ำได้นำเข้า 13 route ได้ที่ mocks/mockoon.json แต่ค่าตัวอย่างเป็นค่าว่าง (ผิด schema ของเราเอง) ต้องแก้มือ และ mock ไม่จำสถานะทดสอบ flow จริงไม่ได้ (login ผิดก็ได้ 201) จึงยังไม่ใส่ในชุดเทส
HAR ของ Playwrightบันทึกการคุยกับ API ครั้งหนึ่งแล้ว replay ให้หน้าเว็บคล้าย characterization ของฝั่ง front end: ล็อก "คำตอบที่หน้าเว็บคาดไว้"npm run test:har หน้าเว็บทำงานครบโดยไม่แตะ API และ request ที่ไม่ได้บันทึกถูกตัดทิ้งให้เห็นเล่นซ้ำลำดับที่สถานะเปลี่ยนไม่ได้ และไม่ได้ทดสอบ back end

ต่างจาก characterization ตรงไหน: characterization บันทึก "สิ่งที่ระบบทำจริงวันนี้" โดยไม่มีสเปกมาก่อน ส่วน Prism ตรวจกับสเปกที่คนเขียนไว้ก่อน ถ้าไม่ตรงต้องตัดสินว่าสเปกผิดหรือโค้ดผิด และ Mockoon กับ HAR เป็นเครื่องมือสร้างฉากให้เทสรันซ้ำได้ ไม่ใช่ตัวเฉลย ที่ลองแล้วใช้ได้ผลจริงที่สุดคือ Prism ผลการลองทั้งหมดอยู่ที่ traffic-recording.md

Characterization กับ Contract ใช้คู่กันตอนแยกระบบ

ตอนตัด service เก่าไปเป็นใหม่ (Strangler Fig): ยิง input เดียวกันเข้าตัวเก่าและตัวใหม่ ผลต้องตรงกัน (characterization) และ API ของตัวใหม่ต้องไม่ผิดข้อตกลงกับ frontend/mobile (contract)

06ข้อควรระวัง

  • อย่าถือว่าเขียวคือถูกต้อง characterization ผ่านแปลว่า “เหมือนเดิม” ไม่ใช่ “ถูก” ส่วนที่เป็นบั๊กต้องมีเจ้าของตัดสิน ไม่ปล่อยค้างเป็น QUIRK ตลอดไป
  • ล็อกมากเกินไปเปราะ เทียบทั้งก้อนจะแดงเมื่อมีฟิลด์ใหม่ ซึ่งต่างจาก contract แบบ consumer-driven ที่ฟิลด์เพิ่มมักไม่พัง (ใน testover schema เป็น .strict() โดยตั้งใจ ฟิลด์ใหม่จึงเป็นการเปลี่ยน contract อย่างรู้ตัว)
  • ภาพแดง ≠ บั๊กเสมอไป ตัดสินแบบเดียวกัน ตั้งใจ → update baseline, ไม่ตั้งใจ → แก้ UI
  • การอัปเดต master ต้องผ่านการตัดสินใจ ไม่รัน --update-snapshots เพื่อให้เขียว
  • เป็นนั่งร้าน เมื่อโมดูลสะอาดแล้ว ควรแทนด้วย unit test ที่บอกเจตนา

ใน testover มีทั้งสองแบบ: assertion ตรง ๆ ต่อพฤติกรรม (validation, resilience) ซึ่งอ่านเจตนาง่าย และ Golden Master (golden-master.spec.ts) ที่เทียบ state ทั้งก้อน (localStorage + ข้อมูลฝั่ง server) กับ snapshot เพื่อจับฟิลด์ที่ไม่มีใครนึกถึง ผ่าน toMatchSnapshot() ของ Playwright พร้อม mask timestamp/UUID และเรียงคีย์ให้นิ่ง ไฟล์ snapshot เป็นข้อความ จึงสร้างบน OS ไหนก็ได้ (ต่างจาก visual ที่ต้องสร้างใน Docker Linux) อัปเดตด้วย npm run test:characterization -- --update-snapshots แล้วอ่าน diff ก่อน commit ทุกครั้ง ข้อควรระวัง: snapshot ไม่มีรหัสผ่านอีกแล้ว (server เก็บเป็น hash และ API ไม่ส่งออก) การพิสูจน์ว่ารหัสเปลี่ยนจริงจึงอยู่ใน assertion ที่ login ด้วยรหัสใหม่
