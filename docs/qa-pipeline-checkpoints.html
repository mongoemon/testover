                  ที่มา: [5][7][9][13][14][15]

                  Build ครั้งเดียว โปรโมตตัวเดิม

                  ตัวที่เทสผ่านใน test และ staging ต้องเป็น artifact เดียวกับที่ขึ้น production ระบุด้วย commit SHA หรือ version

                  ไม่ควร: build ใหม่ตอน deploy prod

                  Gate ต้องบังคับจริง

                  check ที่สำคัญต้องตั้งเป็น required check ใน branch protection ไม่ใช่แค่โชว์สีแดงแล้วยัง merge ได้

                  ไม่ควร: ใส่ continue-on-error ให้เทสหลัก

                  Flaky test ต้องมีเจ้าของ

                  เทสที่ผ่านบ้างไม่ผ่านบ้าง ให้กักไว้ (quarantine) พร้อม ticket และกำหนดวันแก้ ไม่ใช่กด re-run จนเขียว

                  ไม่ควร: retry 3 รอบเงียบ ๆ ทุกเทส

                  ผลต้องอ่านได้โดยไม่ต้องเปิด log

                  มี report รวม เช่น Allure พร้อม screenshot, trace และ video ตอน fail เก็บย้อนหลังพอเทียบแนวโน้มได้

                  ไม่ควร: ไล่ log 3,000 บรรทัดหาว่าอะไรพัง

                  ข้อมูลเทสและ environment ควบคุมได้

                  seed ข้อมูลใหม่ทุกรอบ ไม่พึ่งข้อมูลค้างจากรอบก่อน และ config ของแต่ละ env ต้องตรวจย้อนได้

                  ไม่ควร: เทสผ่านเพราะมีข้อมูลที่ใครสร้างไว้เมื่อวาน

                  ห้ามทำให้เขียวด้วยการลบเทส

                  PR ที่ลบหรือ skip เทส ต้องเขียนเหตุผลไว้และให้ QA รีวิว เทสที่หายไปคือ coverage ที่หายไป

                  ไม่ควร: test.skip โดยไม่มี ticket

                  จำสั้น ๆ: QA ตรวจ pipeline 3 อย่าง คือ ลำดับ (ถูกก่อนแพง) ประตู (แดงแล้วหยุดจริง) และ หลักฐาน (report บอกได้ว่าเทสอะไร กับ version ไหน ผลเป็นยังไง)
