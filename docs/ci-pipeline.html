ให้ CI บอกผลเร็วที่สุด

smoke.yml เดิมรันทุกอย่างเรียงใน job เดียว ตอนนี้แยกเป็น unit, contract, characterization และ smoke-e2e เรียงจากถูกไปแพง รันขนานกันเมื่อทำได้ และมี check เดียวให้ตั้งเป็นเงื่อนไข merge

สั้นๆ: สิ่งที่ถูกและเร็วรันก่อน ถ้าพังก็หยุดตรงนั้น ไม่เสียเวลารัน browser ที่เหลือ · contract กับ characterization แยกกัน เพราะพังแล้วต้องรับมือคนละแบบ

หลักคิด 4 ข้อ

  • ถูกและเร็วก่อน: unit ไม่ใช้ browser ใช้ไม่กี่วินาที ถ้าพังตรงนี้ job แพงๆ จะไม่ถูกรันเลย (needs)
  • ขนานด้วย job ไม่ใช่ step: job ที่ไม่ต้องรอกันรันพร้อมกันบนเครื่องคนละเครื่อง ผลรวมจึงเท่ากับ job ที่ช้าที่สุด ไม่ใช่ผลบวก
  • เทสที่ให้ข้อมูลมากสุดต่อวินาทีมาก่อน: ข้อตกลงที่ขอบเขต (contract) บอกว่าฐานยังดีไหม ก่อนจะไปดูรายละเอียดพฤติกรรม (characterization)
  • check เดียวสำหรับ merge: job smoke รวมผลทุก job จะเพิ่มหรือเปลี่ยนชื่อ job ย่อยทีหลังก็ไม่ต้องไปแก้ branch protection

ผังลำดับ

unit กับ contract รันพร้อมกัน ถ้าผ่านทั้งคู่ characterization กับ smoke-e2e จึงเริ่มและรันพร้อมกัน

ตัว smoke ต้องการทุก job จึงแดงเมื่อมี job ใดแดงหรือถูกข้าม ส่วน report รันเสมอ (แม้เทสพัง) เพื่อให้มีรายงาน Allure รวมไว้ดู

แต่ละ job ทำอะไร

จำนวนเคสนับเมื่อ 2026-10-18 ตัวเลขเปลี่ยนบ่อย นับใหม่ด้วยคำสั่งด้านล่างก่อนยกไปอ้างที่อื่น

jobรันอะไรต้องรอเคสทำไมอยู่ตรงนี้

characterization--grep @characterization (พฤติกรรม legacy + golden master)unit, contract46รันเมื่อข้อตกลงยังเป็นจริง อ่านผลที่พังได้ตรงไปตรงมาขึ้น

นับใหม่ / รันแบบเดียวกับที่ CI รัน:

npm run test:unit
npx playwright test --grep @contract
npx playwright test --grep @characterization
npx playwright test --grep @smoke
npx playwright test --grep @contract --list     # นับเคสโดยไม่รัน

ทำไมแยก contract กับ characterization

ทั้งคู่ต้องผ่านก่อน merge แต่ความหมายและวิธีรับมือเมื่อพังต่างกัน จึงแยก tag, job และรายงานออกจากกัน

contractcharacterization
ตอบคำถามข้อตกลงที่ขอบเขตยังเป็นจริงไหมพฤติกรรมเดิมเปลี่ยนไหม
อายุถาวรชั่วคราว เป็นนั่งร้านระหว่าง refactor แล้วเลื่อนขั้นเป็นเทสจริงหรือลบ
สิ่งที่ pinschema ที่ตกลงกัน (zod, OpenAPI)สิ่งที่เกิดขึ้นจริง รวมถึงส่วนที่ผิด (golden master)
เมื่อพังโค้ดผิดข้อตกลง หรือต้องเจรจาแก้ข้อตกลงบั๊กที่เพิ่งใส่ หรือการเปลี่ยนที่ตั้งใจ ต้องดู diff แล้วตัดสิน
ห้าม update golden master อัตโนมัติใน CI ให้ update ในเครื่อง (--update-snapshots) แล้วให้คนอื่นดู diff ของ snapshot ใน PR ถ้า CI แก้เองได้ มันจะเปลี่ยนให้ผ่านทุกครั้งและเทสหมดความหมาย

job ไหนแดง หมายความว่าอะไร

เปิดแท็บ Actions ของ PR ดูว่า job ใดแดง แล้วทำตามตาราง

jobหมายความว่าทำอะไร
unitlogic, schema, สัญญา report/webhook หรือ API เสียอ่านข้อความ assertion แล้วแก้โค้ด รันซ้ำด้วย npm run test:unit job ที่เหลือจะถูกข้าม
contractข้อมูลที่ขอบเขตไม่ตรง schemaถ้าโค้ดผิดก็แก้โค้ด ถ้าตั้งใจเปลี่ยนข้อตกลงให้แก้ contracts/schemas.mjs กับ contracts/openapi.yaml และบอกฝั่งที่ใช้ API
characterizationพฤติกรรมเดิมเปลี่ยนดู diff ของ snapshot ถ้าเป็นบั๊กให้แก้โค้ด ถ้าตั้งใจให้ update ในเครื่องแล้วให้ reviewer ดู
smoke-e2eเส้นทางหลักของผู้ใช้ใช้ไม่ได้โหลด artifact report-smoke-e2e แล้วเปิด trace: npx playwright show-trace <ไฟล์>

artifact ที่ได้ทุกรอบ (เก็บ 7 วัน): report-<job> = HTML report + trace/video, allure-results-<job> = ข้อมูลดิบ, allure-report = รายงาน Allure รวม ตารางสรุปผลอยู่ที่หน้า run ของแต่ละ job

ตั้งค่าและดูแล

  1. ตั้ง check ที่ต้องผ่านก่อน merge

    GitHub → Settings → Branches → Branch protection rules → Require status checks แล้วเลือกเฉพาะ smoke ตัวเดียว (ชื่อเดิม ไม่ต้องตั้งใหม่) ไม่ต้องเลือก job ย่อย เพราะ job ที่ถูกข้ามเพราะ job ก่อนหน้าพังจะไม่ถูกนับว่าผ่าน แต่ smoke จับให้เอง ถ้าเลือก job ที่ถูกข้ามไว้ PR จะค้างรอตลอด

  2. ชิ้นส่วนที่ใช้ซ้ำ

    .github/actions/setup = Node 22 + npm ci + (ถ้าขอ) Chromium พร้อม cache ตามรุ่น Playwright · .github/actions/playwright-artifacts = ตารางสรุป + อัปโหลดรายงาน ทั้งสองถูกเรียกจากทุก job จึงแก้ที่เดียว

  3. เพิ่ม job หรือกลุ่มเทสใหม่

    ติด tag ให้เทส (ดู tags.md) แล้วคัดลอก job smoke-e2e เปลี่ยน --grep กับ name: ของ artifact จากนั้นใส่ชื่อ job ใหม่ใน needs ของ report และ smoke

ยังไม่ได้ทำ / ควรรู้

บอกตรงๆ ว่าอะไรตรวจแล้ว อะไรยัง

  • ยังไม่ได้รันบน GitHub จริง ตรวจแล้วว่า YAML ถูกต้องและคำสั่งของแต่ละ job ผ่านในเครื่อง (15 / 46 / 5 เคส และ unit 116) รอบแรกบน PR ให้ดูว่า cache ของ browser ทำงาน (รอบที่สองควรเร็วขึ้น) และ artifact ชื่อถูกต้อง
  • weekend-e2e.yml ยังเป็น job เดียว และรัน Playwright ก่อน unit โดยตั้งใจ เพราะ contract C2 ต้องใช้ results.json จริงจากรอบ Playwright ถ้าช้าเกินไปค่อยแยกเป็น job และ shard
  • ยังไม่ shard ตอนนี้ทุก job สั้น พอ E2E เกินราว 10 นาทีค่อยใช้ matrix --shard=1/4 ถึง 4/4 แล้วรวมด้วย merge-reports
  • visual regression ยังไม่อยู่ใน PR เพราะ baseline สร้างจาก Linux/Docker เท่านั้น และ Prism (npm run contract:prism) ยังไม่ถูกต่อเข้า workflow
  • ยังไม่ได้ใส่ paths-ignore แก้ docs อย่างเดียวก็ยังรันทุก job ถ้าต้องการให้ข้าม ต้องระวังเรื่อง required check ที่ถูกข้าม
