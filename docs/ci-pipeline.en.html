Make CI answer as fast as possible

smoke.yml used to run everything in one job, one step after another. It is now split into unit, contract, characterization and smoke-e2e, ordered cheap to expensive, run side by side where possible, with a single check to require before merge.

In short: cheap and fast first; if it fails, stop there and skip the browser jobs · contract and characterization are kept apart because a failure in each needs a different response.

Four ideas behind it

  • Cheap and fast first: unit needs no browser and takes seconds. If it fails, the expensive jobs never start (needs).
  • Parallel by job, not by step: jobs that do not wait for each other run on separate machines at once, so the total is the slowest job, not the sum.
  • Most information per second first: the boundary agreements (contract) say whether the base is sound before you read the details of behaviour (characterization).
  • One check for merging: the smoke job gathers every result, so adding or renaming a job later does not touch branch protection.

The order

unit and contract run together. When both pass, characterization and smoke-e2e start and run together.

smoke needs every job, so it goes red when any job fails or is skipped. report always runs (even when tests fail) so there is a combined Allure report to open.

Why contract and characterization are separate

Both must pass before merge, but they mean different things and a failure needs a different response, so they get separate tags, jobs and reports.

contractcharacterization
AnswersDo the agreements at the boundary still hold?Did the existing behaviour change?
LifetimePermanentTemporary scaffolding during a refactor; promoted to real tests or deleted afterwards
What it pinsThe agreed schema (zod, OpenAPI)What really happens, including the wrong parts (golden master)
When it failsThe code broke the agreement, or the agreement must be renegotiatedA bug just introduced, or an intended change: read the diff and decide
Never auto-update a golden master in CI. Update it locally (--update-snapshots) and let someone else review the snapshot diff in the PR. If CI could fix it itself it would turn green every time and the tests would mean nothing.

What each red job means

Open the PR's Actions tab, see which job is red, then follow the table.

jobIt meansWhat to do
unitLogic, a schema, the report/webhook contract or the API brokeRead the assertion message and fix the code; rerun with npm run test:unit. The other jobs are skipped.
contractData at a boundary no longer matches its schemaIf the code is wrong, fix it. If you meant to change the agreement, edit contracts/schemas.mjs and contracts/openapi.yaml and tell whoever uses the API.
characterizationExisting behaviour changedRead the snapshot diff. A bug: fix the code. Intended: update locally and have a reviewer look.
smoke-e2eA main user path is brokenDownload the report-smoke-e2e artifact and open the trace: npx playwright show-trace <file>

Artifacts every run (kept 7 days): report-<job> = HTML report + traces/videos, allure-results-<job> = raw data, allure-report = the combined Allure report. The summary table is on each job's run page.

Setup and upkeep

  1. Make the check required before merge

    GitHub → Settings → Branches → Branch protection rules → Require status checks, then pick only smoke (the old name, nothing to reconfigure). Do not pick the individual jobs: a job skipped because an earlier one failed does not count as passed, but smoke catches that for you. If you require a job that gets skipped, the PR waits forever.

  2. Reusable pieces

    .github/actions/setup = Node 22 + npm ci + (on request) Chromium cached per Playwright version · .github/actions/playwright-artifacts = summary table + report upload. Every job calls both, so a change happens in one place.

  3. Add a job or a new group of tests

    Tag the tests (see tags.md), copy the smoke-e2e job, change --grep and the artifact name:, then add the new job to needs of report and smoke.

Not done yet / good to know

What was checked and what was not.

  • Not run on GitHub yet. Checked: the YAML parses and each job's command passes locally (15 / 46 / 5 cases, unit 116). On the first PR, check that the browser cache works (the second run should be faster) and that the artifact names are right.
  • weekend-e2e.yml is still one job and runs Playwright before unit on purpose, because contract C2 needs the real results.json from the Playwright run. Split and shard it only if it becomes too slow.
  • No sharding yet. Every job is short today. Once E2E passes about 10 minutes, use a matrix of --shard=1/4 to 4/4 and join with merge-reports.
  • Visual regression is not in PRs because baselines come from Linux/Docker only, and Prism (npm run contract:prism) is not wired into a workflow.
  • No paths-ignore. A docs-only change still runs every job. If you want it skipped, mind the required check that would be skipped.
