Automation, Phase by Phase
and What Dev × QA Do Together

This page walks through how the testover automation system is built, from choosing what to test to long-term upkeep. It shows where contract and characterization testing happen and what Dev and QA each do at every step.

02Phase details

Every "In testover" line was checked against the files in the repo.

0Choose what to automate (Discover & Risk)

Decide which tests are worth writing as code, and which are not.

QA

  • Walk the key user journeys (register → sign in → manage tasks → edit profile)
  • Rank by risk and how often regression is needed
  • Leave look-and-feel style checks to manual testing

Dev

  • Point out fragile or frequently changed areas
  • Describe the data boundaries (localStorage, APIs) and who owns them
  • Confirm the test environment is repeatable (npm start)

In testover: The main journeys became tests/journey.spec.ts, login, tasks, profile

Exit condition: A risk-ranked list of journeys, and an agreed list of what is not automated.

1Build the foundation (Foundation)

Make the next test fast to write and resilient when the UI changes.

QA

  • Set up Playwright, config and Page Objects (tests/support/pages.ts)
  • Add storage helpers (tests/support/storage.ts)
  • Define tags: @smoke @contract @characterization @security @destructive

Dev

  • Provide stable selectors (role, label, test id), not CSS coupling
  • Make the app start from a known state (seed data / demo account)
  • Announce DOM restructures before merging

In testover: playwright.config.ts, tests/support/, docs/tags.md

Exit condition: A new test can be written with Page Objects without copying selectors.

2Agree the contracts at the boundaries (Contract)

Turn the agreements between parts of the system into runnable code before many tests depend on them.

QA

  • Express each agreement as a zod schema in contracts/schemas.mjs
  • Write tests proving the app and scripts really honour the schema
  • Build fixtures for pass / fail / empty cases

Dev

  • State what valid data looks like (lengths, types, required fields)
  • Review schemas against intent, not just current code
  • Change the schema in the same PR when adding a field

In testover: C1 localStorage (token + theme) → tests/contracts/storage.spec.ts · C4 API JSON → tests/contracts/api.spec.ts (spec: contracts/openapi.yaml) · C2 Playwright report and C3 webhook body → unit/contracts.test.mjs. Schemas are .strict() on purpose, so a new field is a conscious contract change.

Exit condition: Every boundary the system crosses has one schema, imported by both unit tests and Playwright.

3Record current behaviour (Characterization)

Pin what the app actually does today before changing or refactoring it, so any drift is visible at once.

QA

  • Walk the boundaries: username 2/3/20/21 chars, forbidden characters, trim/lowercase
  • Walk abnormal states: corrupt or wrong-typed storage data
  • Name odd behaviours QUIRK: so they are easy to find

Dev

  • Decide case by case whether the behaviour is intended or a bug
  • Bug → open a ticket, then change the test with the fix
  • Intended → keep it and note the reason in a comment

In testover: tests/characterization/validation.spec.ts and resilience.spec.ts and golden-master.spec.ts (5 whole-state snapshots, localStorage plus what the server holds, in tests/__screenshots__/characterization/) and network-golden.spec.ts, 46 tests. Tests named GUARD pin behaviour that used to be a QUIRK and was fixed by the backend, e.g. passwords are now hashed and task ids are never reused. (The unit suite also characterizes the exact notify messages.)

Exit condition: Every boundary you will touch has a passing test of today's behaviour, and each QUIRK has an owner decision.

4Feature-level tests (Unit · E2E · A11y)

Cover the behaviour that is meant to exist, following the pyramid: unit is fast, E2E covers journeys.

QA

  • Write E2E per the journeys ranked in phase 0
  • Add axe accessibility and @security tests
  • Watch for flakiness and weak assertions

Dev

  • Write unit tests for logic that needs no browser (unit/*.test.mjs)
  • Review QA tests against requirements
  • Add tests in the same PR as a new feature

In testover: E2E in tests/*.spec.ts, a11y in tests/a11y.spec.ts. 137 Playwright tests in 10 files (5 smoke, 12 security, 5 visual).

Exit condition: Every new feature has at least one layer of tests before merge.

5Wire into CI (Gate & Report)

Run tests automatically and tell the people who need to know.

QA

  • Choose the PR gate (@smoke) and the scheduled full suite
  • Set up reporting (Allure) and notification (scripts/notify.mjs)

Dev

  • Own workflows, secrets and environments
  • Own a red build on their own PR

In testover: smoke.yml runs unit + smoke + characterization on every push/PR · weekend-e2e.yml runs everything Sat–Sun 09:00 Thailand time with unit, Allure and notification · cloudflare-pages.yml publishes docs and reports

Exit condition: A PR that turns smoke/unit/contract red cannot merge, and the full result reaches the team unprompted.

6Keep it healthy (Maintain)

Stop tests rotting and turn what they reveal into decisions.

QA

  • Triage weekly results: real bug / flaky / outdated test
  • Quarantine unstable tests and chase them
  • Keep tag docs and counts current

Dev

  • When a characterization or contract test fails, decide "fix the app" or "fix the expectation"
  • Fix QUIRKs that are bugs, then rename the test to describe the correct behaviour

In testover: The header of the characterization files says it directly: if one fails, decide deliberately, then update the expectation.

Exit condition: No red test without an owner.

03Contract vs Characterization

They are often confused. The difference is what you treat as the truth.

Contract testing

  • Treats the agreement of what should be as truth
  • Written before or with the design, agreed by Dev and QA
  • Red = one side broke the agreement; fix that side
  • Checked at the edges: storage data, report, webhook
  • Markers: @contract, contracts/schemas.mjs

Characterization testing

  • Treats what the app does today as truth
  • Written afterwards by observing, without judging right or wrong
  • Red = behaviour changed; decide if that was intended
  • Checked at input boundaries: length, characters, corrupt data
  • Markers: @characterization, names starting QUIRK:

When one of these goes red, who does what

Test goes red
↓
Contract or Characterization?
↓
Contract → find who broke the agreement and fix that side, or open a PR changing the schema with reasons (Dev + QA sign off)
↓
Characterization → Dev decides: intended change? update the expectation / bug? fix the app
↓
Update docs and the test name (a former QUIRK gets renamed)

Order: on existing (legacy) code, characterization usually comes before contracts, because you must see reality before agreeing what it should be. testover places Contract at phase 2 because later tests import the shared schemas. The two steps can be swapped without affecting the others.

05Handoffs to agree explicitly

This is where automation usually breaks, when the two sides understand things differently.

SelectorsDev announces DOM changes; QA uses role/label first, test id when needed
Seed dataDev guarantees the demo account and start state; QA never relies on data another test created
Contract changesEdit contracts/schemas.mjs in the same PR as the code, with QA review
QUIRKQA finds → Dev decides "intended/bug" → a ticket or reason is recorded
Definition of DoneA feature has at least one test layer before merge; smoke must be green
Full-suite resultsQA triages weekly; Dev takes the tickets that are real bugs

06Visual snapshot testing

Compare real screenshots with reference images (baselines) to catch UI drift while other tests still pass. It sits in phase 4, after E2E.

What it isA test opens a page, sets up state, then calls toHaveScreenshot() to compare pixels with a committed image. A difference above the threshold (1%) fails it. This differs from screenshot: only-on-failure, which only keeps an image to look at after a failure.
In testovertests/visual.spec.ts, 5 screens tagged @visual: login, register with an error, task board, task board in dark theme, profile. Baselines live in tests/__screenshots__/
Where baselines are madeInside the Playwright Docker image (Linux) via npm run test:visual:update, not on Windows or Mac, because fonts and anti-aliasing differ and would turn CI red.
QA doesChoose screens worth covering, make state stable (fixed data, animations off), and look at every image before committing a baseline.
Dev doesSay when a look change is intended, approve the new baseline in the same PR as the UI change, and flag self-changing values such as version numbers or dates so they get masked.
Watch outA red image is not always a bug. Read the diff and decide as with characterization: intended → update the baseline, unintended → fix the UI. The version badge at the bottom right may change every release.

07Commands

Run a single layer by tag.

npm run test:unit             # unit + C2/C3 contracts (node:test)
npm run test:contract         # all contracts (unit + @contract)
npm run test:characterization # 46 characterization tests
npm run test:smoke            # 5 fast tests for PRs
npm run test:safe             # everything except @destructive
npm run test:visual           # compare 5 screens (in Docker)
npm run test:visual:update    # create/update baselines (in Docker)
npm test                      # full suite, 137 tests
